# ContentPulse UX Audit — 2026-10-23

Audit-only. No application code, config, migrations, tests or data were changed. This file is the only thing created.

**Method and limits.** Static code audit of the frontend (routes, shell, nav, dashboard, trends, topics, content, design, approvals, org setup, account) and the backend pieces that decide user-visible behavior (trend/topic sync, org creation, post/approval labels, auto-analysis, discovery window). I did **not** run the app, log in, use a browser, run tests, or call any provider, so nothing below is visually or interactively verified. No usability testing has been done: anything about "what users will find confusing" is a hypothesis grounded in the code, labelled as such.

**Not inspected (or only skimmed):** landing page and product tour, login/register/invite/reset screens, knowledge-base internals, activity log, team dialogs, design-brief dialog, most backend routers line by line, mobile layouts, contrast, focus order. Existing e2e specs (including `a11y.spec.ts`) were not run.

Note: `AUDIT_REPORT.md` (2026-10-05) already exists in the repo root and covers implementation status, not UX. It was left untouched.

## Deliverable 1 — Executive summary

ContentPulse is already more guided than most tools like it: there is a single workflow list reused by sidebar, dashboard and welcome tour, a "next step" callout, a setup checklist, role-aware empty states, and plain-language status names. The problems are not general clutter. They are a handful of structural issues:

1. **Trends and Topics are the same thing shown twice.** The backend mirrors every trend 1:1 into a "topic" and keeps their shortlist/reject status in sync. The UI gives each its own list, detail page, filters and shortlist/reject buttons, and the detail pages repeat the same analysis, signals and evidence panels. A user shortlists on Trends, then has to know to go to Topics to do the next thing. On shortlisted rows, the only control shown is a delete icon.
2. **The "5 numbered steps" model doesn't match what happens.** Approval happens twice, on either side of Design (copy → design → design approval). Step 4 "Add designs" comes before step 5 "Approve", but the first approval comes before step 4. A post has 11 statuses. The same ideas are named differently on different screens ("Ready to post", "Ready to publish", "Approved to publish").
3. **Onboarding makes a promise the system does not keep.** The create-organization form says the website is used to "build your knowledge base". Creating an organization does not start a crawl; the user must find Knowledge base → Crawl website, and the dashboard checklist later asks for the website again.
4. **The Discover button's label over-promises.** "Discover New Trends now" often does not fetch anything (by design, inside the discovery window). The user only learns this from a toast after clicking. No persistent "last updated / next update" line exists unless background updates are on.
5. **Setup is spread across six pages with overlapping fields**, including a "Scheduling timezone" that has no consumer in the backend (scheduling is not implemented).
6. **A few stale or misleading strings and one partial-success hazard** (multi-platform "Write N posts" can leave saved plans behind and duplicate them on retry).

Biggest opportunities: collapse Trend→Topic into one visible journey, show each post's position in the real 6-stage path, make onboarding honest and shorter, and make the discovery action say what it will do. None of these require removing a capability or adding LLM/provider calls. The most valuable ones are mostly frontend-only.

Overall state: solid foundation, mature copy in many places; the friction is concentrated in the Trend→Topic→Plan handoff, the two-stage approval, and the setup area.

Dashboard · **Content workflow** (Find trends [+ Discovery Sources], Pick topics, Write posts, Add designs, Approve) · **Set up your organization** (collapsible: Profile, Content setup, Services & products, Brand, Platform playbook, Knowledge base) · **Team & account** (collapsible: Team, Activity log, Settings). ### Roles
Admin, Creator, Viewer (see `PRODUCT.md`); designer capability is `design.upload`.

### Core journey
Trend → (auto-created Topic) → shortlist → post plan per platform → Write post (AI/template) → Submit for approval → **Content approval** → design task opens automatically with brief → export brief / upload / AI image → submit → **Design approval** → "Ready to publish" → Share (manual).

### State machines seen
- Trend: new → analyzed → shortlisted / rejected / archived.
- Topic: new / reviewed → shortlisted / rejected / archived (mirrored with trend by `services/topics/sync.py`).
- Post (11): draft, content_review, design_pending, design_in_progress, design_uploaded, pending_approval, changes_requested (design only), approved (legacy), final, rejected, archived (`lib/content.ts`).
- Approval: stage copy|design × pending/approved/changes_requested/rejected.

### Backend facts that shape UX
- Auto-analysis after ingestion (`alignment_auto_analyze=True`, `workers/trend_tasks.py:295`), so manual "Analyze now" is mostly a fallback/retry.
- Discovery has a window: clicking Discover inside it reloads stored trends (`trends-explorer.tsx:322`).
- Org creation creates settings/brand/member only; no crawl (`services/organization/organizations.py`).

### High-severity findings in detail

**UX-001 Trend and Topic duplicate each other.**
- *Current:* `sync_from_trend` creates a topic for every relevant analyzed trend; `on_trend_status`/`on_topic_status` mirror shortlist/reject both ways. UI: `/trends` (Active/Shortlisted/Rejected tabs) and `/topics` ("To review"/Shortlisted/Rejected) are two views of the same records with the same buttons. `TrendDetailView` and `TopicDetailView` both render `AlignmentPanel`, signals and evidence.
- *User problem:* "Which page do I decide on?" Shortlisting on Trends gives a toast "It's in Topics now", then the user must navigate. Topics "To review" is a second triage pile of items already triaged on Trends. Post ideas on the trend page have no "plan" button; on the topic page they do.
- *Root cause:* Data model split (trend vs candidate topic) leaked into UI.
- *Recommendation:* Keep both tables and API contracts. Make the UI one journey. Option A (recommended): Trends is the only triage screen; shortlisting a trend reveals a "Plan posts" section on the trend detail (the strategy cards and post list moved/embedded); "Topics" becomes "Shortlist" (trends you're working on, with plans/posts progress) rather than a second review queue. Option B: remove the Trends shortlist button and make Topics the triage screen. Option C: only fix UX-005/006 (cheapest; leaves duplication).
- *Benefit:* One decision per item, one place for the next step.
- *Risk:* Role split (`trends.manage` vs `topics.manage`), existing deep links (`/topics/[id]`, back-links via `from`), e2e specs (`trends.spec.ts`, `workflow-labels.spec.ts`), dashboard counts (`topics_to_review`). Do not delete the topic table/API.
- *Effort:* Large (A/B), Small (C).

**UX-002 Journey numbering vs actual flow.**
- *Evidence:* `WORKFLOW` numbers Write(3) → Design(4) → Approve(5); `review-page.tsx` shows content approval opens design; design approval is a second pass on the same Approve page (`approval-list.tsx` tabs "Content approval / Design approval / Ready to post"); 11 post statuses.
- *Problem:* A user who "approved" a post sees it again in "Add designs" and then again in "Approve". Whether their post is waiting for them or someone else is not obvious from the nav.
- *Recommendation:* (1) Per-post progress tracker on post/design/approval pages: Plan → Write → Content approval → Design → Design approval → Ready, with "who acts next". (2) Reword nav step summaries to say approval happens twice; drop numeric order for steps 4–5 or label them "Design" and "Approvals (copy and design)". (3) Optionally a single "Posts" board later (Phase 3, needs validation because roles differ).
- *Risk:* Low for (1)/(2): purely presentational from existing `status` and `review`/`design_task` fields. (3) touches permissions.
- *Effort:* M.

**UX-003 Onboarding promise vs behavior.**
- *Evidence:* `create-organization.tsx` hint "We'll build your knowledge base from it."; `create_organization` adds org, settings, brand, member only; crawl is started from `knowledge-base.tsx` "Crawl website"; checklist step "Add your website to the knowledge base".
- *Problem:* User reasonably believes it's done; later gets a to-do for something they believe they already did. Ungrounded posts (key product promise) result.
- *Recommendation:* Now: change hint to "You'll be able to index this website next." Better: on the checklist step, a single "Index my website" button that opens the existing crawl dialog prefilled. Auto-starting a crawl at creation is a backend/cost decision (needs approval).
- *Effort:* S (copy) / M.

**UX-004 Discover label.**
- *Evidence:* Button text `"Discover New Trends now"` (`trends-explorer.tsx:157`); inside the window the result is a toast "No new trends found since the last discovery… available in X" (`:337`). Button is also disabled when no source is on, without saying why (`:153`), though the empty state does.
- *Problem:* A button that says "now" and "New" but often reloads cache; user retries, learns the rule from a toast. Respecting the window is correct; the label/feedback is the issue.
- *Recommendation:* Persistent line under the header: "Last updated 14:05 · next update about 17:05" (data already available via `useDiscoveryWindow`); button label "Check for new trends"; when inside window, button shows "Next update at 17:05" disabled-with-reason or stays clickable but secondary. No extra API requests (window data already fetched).
- *Effort:* S. *Risk:* none to caching; don't make the button hit providers.

### Remaining medium/low findings — evidence notes
- **UX-005:** `TrendActions` returns only `deleteButton` for `shortlisted` (trend-row.tsx); `TopicActions compact` does the same. Rows already link to detail, but the visible control on a shortlisted row is destructive.
- **UX-007:** `submitWith` loops `create.mutateAsync` for each platform, then optionally `generate.mutateAsync`; `catch` shows `toast.error` only; dialog remains open with form state; retry recreates all selected platforms. Confidence Medium because I did not execute it.
- **UX-008/009:** strings: dashboard "ready to publish" and "Approved to publish"; approvals tab "Ready to post"; status "Ready to publish"; toast "the post is in Ready to post". "Content" = nav route `/content` (Write posts), "Content setup", "Content approval", "Content goals".
- **UX-011:** `default_timezone` appears only in model/schema/settings form; no service reads it (grep). `PRODUCT.md` lists scheduling as undecided.
- **UX-013:** sources page shows `Set on the server: <ENV_VAR>` chips to all roles; footer says keys "stay managed by ContentPulse".
- **UX-014:** `<HowItWorks />` rendered unconditionally; dashboard has KPIs + TrendingTopics + ContentPipeline + RecentContent + TopOpportunities + SourceHealth + PlatformBreakdown. Positive: new orgs get a simplified view (`isNew`).

### Things that work well (keep)
Workflow list single source of truth; setup checklist with progress; "next step" callout; role-aware empty states; explicit content vs design approval wording in status labels; plain "Does this fit your business?" panel with evidence and "Avoid saying this" claims; clear approval locking messages; honest AI/rule fallback labelling; source status pills with text not color alone; stored filters per page.

### Technical defects (report only, not UX)
UX-007 (duplicate plans on retry), UX-011 (dead control), UX-010 (stale copy), UX-003 (misleading promise). No security or isolation issue was identified, but I did not audit authz.

## Deliverable 4 — Current-state journeys

**First-time admin.** Register → `/onboarding` (5 fields, good, minimal) → Dashboard with welcome tour (3 screens) + "Next step" callout + "Set up your workspace" checklist (6–7 items across 6 pages) + HowItWorks. Likely drop-off points: (a) believes website already indexed (UX-003); (b) setup pages are many and fields overlap (UX-012); (c) first Trends visit with no runs yet shows an empty state with a clear "Discover" button (good), but waiting "a minute" has no progress indicator beyond the button label "Discovering…".

**Returning creator.** Dashboard callout → Trends (filter defaults to "Relevant to us") → Shortlist (toast) → must go to Topics or click the toast action → open topic → plan per platform (form) → Write post → studio → Submit for approval → leaves: nothing to do until approval → later Design page ("Designs to create") → Approvals. Repeated/confusing: shortlist/reject exist twice; "Approval status" tab appears in Write and in Design.

**Returning admin.** Dashboard callout leads to Approvals; reviews content (Approve content), returns later for design approval; legacy "Mark ready to publish" only for old posts.

**Dead ends:** Design list empty text points to a non-existent "send to design" action; "Ask your administrator to turn on AI" without a place to do it; shortlisted rows with only Delete.

## Deliverable 5 — Proposed simplified experience

### Navigation

```
Home (dashboard)
Trends                      ← discover, triage, and plan posts for shortlisted
  └ Discovery Sources       (fold-out, unchanged)
Shortlist & plans           ← (renamed Topics; not a second review queue)  [decision D1]
Posts                       ← (renamed Write posts)
Designs                     ← (renamed Add designs)
Approvals                   ← copy and design approvals; Ready to publish
──
Business setup (collapsible)
  Business profile          ← Profile + Content setup (audience, markets, keywords, platforms)
  Services & products
  Brand
  Knowledge base
  Platform rules  (advanced)
Team & account (collapsible)
```
Per-post progress tracker (shown on post, design and approval pages):
`Plan ✓ → Write ✓ → Content approval ● → Design → Design approval → Ready to publish` with "Waiting on: an admin".

### Onboarding
Keep the 5-field form. Change the Website hint. After creation, land on Dashboard with checklist: 1 Services, 2 Index website (one click, prefilled), 3 Brand voice, 4 Markets/audience, 5 Platforms; invite team stays optional. Make "Describe your organization" auto-done when onboarding captured it (already so). No wizard.

### Trends
Header: title, one line of purpose, **Last updated · next update** line, primary "Check for new trends" (reason shown when unavailable), settings toggle moved into Sources page (or kept but secondary). Filters: status tabs + Relevance (4 options) + "More filters" for source/location/sort. Row: score, title, relevance badge, one-line why; primary action by state: New → Shortlist; Shortlisted → Plan posts; Rejected → Restore. Delete only in the overflow menu.

### Trend → content
Shortlist → Plan section on the same trend/topic page → "Write post" auto-drafts plan fields; "Adjust plan" collapsed. Multi-platform write reports per-platform results.

### States
- Loading discovery: "Collecting from N sources… usually under a minute" with per-source results afterwards.
- Cached: "Showing trends from 14:05. Next check about 17:05."
- Failure: "2 of 5 sources failed (Reddit rate limited). Showing results from the rest. Try again after 17:05."
- AI quota out: "AI is unavailable right now. Using keyword matching; ideas will be basic." plus who can fix.
- Saved: inline "Saved" for editors.

### Keep separate
Trends vs Posts vs Designs vs Approvals (different roles); Knowledge base; Brand; Services; Team.

## Deliverable 7 — Acceptance criteria

1. Before clicking, a user can tell when trends were last updated and when the next update is due; the discovery button never triggers a provider call inside the window (verified by `test_discovery_window` and network inspection).
2. A new admin can reach "website indexed" in one action from the dashboard, and no screen claims indexing happened when it didn't.
3. From a shortlisted trend, "Plan posts" is reachable in one click and no row shows Delete as its only action.
4. Every post page shows its stage in the 6-stage path and who acts next.
5. One term for the final state ("Ready to publish") across dashboard, approvals, status, toasts.
6. A multi-platform write that partly fails reports which platforms succeeded and does not create duplicates on retry.
7. No field is shown whose value is never used (Scheduling timezone).
8. No new LLM or provider requests introduced; org isolation, permissions and API contracts unchanged (existing tenant-isolation and permissions tests pass).
9. Moderated test: ≥4 of 5 new users complete trend → approved copy without help.
